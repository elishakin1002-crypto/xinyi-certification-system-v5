# 信义认证系统 · 上线就绪计划

> 一条命令：`npm run readiness`
> 加 `--fast` 跳过备份演练（约省 6 秒，日常自查用）。

---

## 为什么需要这个

2026-08-22 之前，仓库里有 25 个 `health:` / `check:` 开头的命令，散着。
问题不是检查不够，是**没有闸门**——没人知道该跑哪几个、什么顺序、跑完算不算「可以上线」。

更说明问题的是当天的实际情况：一天里查出 7 个真 bug，**没有一个是系统性找出来的**，
全是干别的时候撞见的。其中几个的后果是：

- 销售角色**根本建不出来**（传 `SALES` 被静默存成 `CONSULTANT`）
- 改员工角色、重置密码被当成「读操作」，归属限制完全失效
- 事务接口收 5 个数据集只写 4 个，工作日志被静默丢弃
- 切 enforce 后销售建不了合同、顾问在自己项目上建不了任务

靠「用着用着发现」找这类问题，代价是同事在上线后替你踩。

---

## 参考了谁

两套成熟做法，不是自己拍脑袋定的：

**[Google SRE 的 launch checklist](https://sre.google/sre-book/launch-checklist/)**——架构与依赖评审、
失效模式逐个推演、容量、回滚机制、备份恢复，按风险分级决定评审深度。
关键一句：*一次上线不应该是这条告警、这个通知路径、这份处置手册第一次被真正跑起来的时刻。*

**ERP/CRM 的 go-live gate**——数据迁移必须由**业务方**验收（不是技术方说导完了就算完）、
角色要按真实岗位场景测（**不能只用管理员账号**）、切换要预演、回滚要有时限、
上线后有观察期（hypercare）。

信义的实际情况决定了权重：内部系统、几个人用、200–400 合同/年，
**容量根本不是问题**。真正会出事的是两件事：**数据对不对**、**人能不能干活**。
所以闸门按这两件事排。

## 五道闸门（机器验）

| 闸门 | 查什么 | 为什么它排在这个位置 |
|---|---|---|
| 1 数据就绪 | 演示残留、孤儿引用、PG 与镜像一致、迁移最新 | 上线第一天看到的数字必须是对的，错一次没人再信这个系统 |
| 2 身份与权限 | **enforce 模式下四个岗位各跑一遍自己的活**、权限矩阵自洽、观察期越权记录 | 切 enforce 那天每个人都得能干活 |
| 3 代码就绪 | 类型检查、全量测试（走真实 PG 路径） | 最便宜的一道网，破了后面几道不用谈 |
| 4 界面就绪 | 文案占位、各角色视图渲染 | 同事只通过界面用系统，界面错了等于系统错了 |
| 5 失效与恢复 | 备份恢复演练 | 备份没演练过等于没有备份 |

### 闸门 2 是这套东西的核心

`npm run test:enforce` 让**每个岗位用自己的账号**把当天的活跑一遍：

```
销售   建线索 → 记跟进（自动认领）→ 转客户 → 建合同
顾问   看项目 → 建任务 → 完成任务 → 进度归零到 100
财务   看合同金额 → 对账
```

用管理员测权限系统，就像用万能钥匙测门锁——他的读写范围都是 `ALL`，
把授权层整个绕过去了。2026-08-22 第一次跑 enforce 演练，销售和顾问**双双跑不通**，
两个 bug 当场现形。observe 模式下这两条是绿的，因为它本来就一律放行。

## 已知并接受的风险

上线前不可能把问题清零。做法是**显式登记并接受**，写在 `scripts/health-data.mjs`
的 `ACCEPTED` 表里，每条必须说明三件事：为什么可以带着上线、什么时候重新评估、后果是什么。

当前 1 条：

> **工作日志 / 不符合项 / 任务模板没有专用 PG 表**，数据存在状态存储的 JSONB 里。
> 数据不会丢，读写正常；缺的是 SQL 统计能力和数据库约束。
> 按当前数据量（53 / 1 / 4 条）不影响使用。
> 解决时点：待办 P0-19，建议上线稳定后一个月内。

两条纪律：

- 假装问题不存在会让人不再相信告警
- 一个永远变不成绿的闸门等于没有闸门

`ACCEPTED` 这张表变长，就是在悄悄降低标准。加条目要有明确理由。

## 机器验不了的五条

**这五条一条没做就上线，出事时没有退路。** 机器全绿只说明系统自己没发现问题。

### 1. 数据真实性 — 业务方当面核对

抽 **10 条真实客户 / 合同**，由老板或经办人核对金额、日期、负责人。

行业原话：*数据迁移不算完成，直到业务负责人能验证他们日常要用的那些记录。*
技术侧说「导完了、条数对得上」不算数——条数对得上、金额错一位，一样是灾难。

### 2. 岗位试用 — 真跑，不是看演示

每个岗位的同事用**自己的账号**，把当天的活真做一遍。

看演示时人会跟着操作者的思路走，不会撞到真实的卡点。
让他自己上手，卡在哪一步一目了然。

### 3. 回滚决定权 — 写下来

出事时**谁有权喊停**、**多久内**必须恢复到旧方式。

写下来并让所有人知道。没写下来的结果是：出事时大家都在等别人拍板。
行业里常见的口径是「4 小时内可执行回滚」，信义可以定得更宽，但必须有个数。

### 4. 观察期安排（hypercare）

上线后头两周：谁盯、每天看什么、发现问题找谁。

建议每天跑一次 `npm run readiness -- --fast`，并看一眼
`npm run authz:report`（有没有人被权限挡住）。

### 5. 旧方式并行

前两周旧的记录方式（表格 / 微信）保留，作为对不上时的退路。

不是不信任新系统，是给自己留一条不用连夜救火的路。

## 日常怎么用

```bash
npm run readiness -- --fast    # 日常自查，约 80 秒
npm run readiness              # 上线前完整跑，含备份演练
npm run readiness -- --gate 2  # 只验权限
```

退出码非 0 = 有阻断项，不要上线。

---

## 上线当天的顺序

1. `npm run backup` — 先备份，且确认备份在**另一台机器上**
2. `npm run readiness` — 全绿
3. 五条人工确认逐条过一遍，有人签字
4. 切 `XINYI_AUTHZ_MODE=enforce`，重启后端
   （切之前先改 `server/authz/middleware.js` 里「判定异常时放行」的兜底——
   observe 阶段那是刻意的，enforce 阶段必须改成出错即拒绝）
5. 立刻再跑一次 `npm run readiness -- --gate 2` 确认权限没把人挡住
6. 进入两周观察期
