> 出事那天没人有心情读长文档。这份只写「怎么做」，原理放最后。
> 最后一次演练：**2026-08-17 通过**（12 张表 / 1233 行 / 附件逐字节一致）

## 三条命令

```bash
npm run backup        # 备份：数据库 + 附件 + 指纹
npm run backup:drill  # 演练：备份→临时库→逐表比对→自动清理（不碰生产）
npm run restore -- --from <备份目录> --target <目标库URL>   # 真出事时用
```

## 一、日常备份

```bash
npm run backup
```

产物在 `.runtime/backups/xinyi-<时间戳>/`：

| 文件 | 内容 |
|---|---|
| `database.dump` | pg_dump 自定义格式，已压缩，支持单表恢复 |
| `uploads.tar.gz` | 合同附件、审核证据等磁盘文件 |
| `state/` | JSON 状态文件（见下方警告），逐个复制 |
| `manifest.json` | 每张表的行数 + 内容校验和 + 状态文件清单，恢复时逐项比对 |

> ⚠️ **不是所有数据都在 PostgreSQL 里。** 2026-08-17 排查发现：工作日志（29 条）、
> 不符合项、任务模板、AI 决策日志只写 `state_store.json`，PG 对应的表是空的；
> 员工账号只在 `auth_store.json`。只备份 PG 的话这些一份都救不回来——
> 而工作日志和不符合项恰恰是最值钱的那部分数据。
> 备份已包含这些文件；持久化本身要修（待办 P0-19）。

**备份必须挪出本机。** 默认写在项目目录里只是图方便——服务器整台挂掉时，存在同一台机器上的备份跟着一起没。至少同步到另一块盘或另一台机器：

```bash
npm run backup -- --out /mnt/backup/xinyi
```

### 频率建议

| 阶段 | 频率 | 保留 |
|---|---|---|
| 测试期 | 每天一次 | 7 天 |
| 正式运营 | 每天一次 + 每周一次异地 | 日备 14 天，周备 3 个月 |
| 改表/升级/迁服务器**之前** | 手动跑一次 | 直到确认新版本稳定 |

## 二、恢复演练（**每月必跑**）

```bash
npm run backup:drill
```

它会备份 → 建一个临时库 → 恢复进去 → 逐表比对 → 删掉临时库。**全程不碰生产库。**

看到这个才算通过：

```
✅ 演练通过：1233 行数据完整恢复，内容校验和逐表一致。
```

**任何一行出现 ✗ 就说明备份不可信，当天必须查清楚。**

> 为什么非要演练：备份脚本能跑通 ≠ 备份能用。
> 常见的坏法是「备份天天在跑，出事那天才发现恢复不了」——
> 权限不对、版本不兼容、附件没备进去，这些只有真恢复一次才会暴露。

### 账号没有建库权限时

演练会提示，改用人工建的空库：

```bash
npm run restore -- --from <备份目录> --target postgres://用户:密码@主机:5432/演练用空库
```

## 三、真出事了怎么恢复

**先停应用，再恢复。** 一边写一边恢复必然对不上。

```bash
# 1. 停服务
# 2. 恢复到目标库
npm run restore -- --from .runtime/backups/xinyi-20260817-065018 \
                   --target postgres://用户:密码@主机:5432/xinyi \
                   --i-know-this-overwrites-production
# 3. 看到「✅ 恢复校验通过」再启动服务
```

### 三道防手滑保护

| 情况 | 结果 |
|---|---|
| 不写 `--target` | 拒绝执行——绝不「默认恢复到当前库」 |
| `--target` 与当前配置的库同名 | 拦下，要求补 `--i-know-this-overwrites-production` |
| 恢复后指纹对不上 | 报错退出，不给「看起来成功」的假象 |

### 只想确认备份完好、不想写库

```bash
npm run restore -- --from <备份目录> --target <某个空库> --verify-only
```

## 四、部署到服务器要注意的

### 1. pg 客户端版本要和服务端一致

脚本会自检并提示：

- 客户端**低于**服务端 → **直接拒绝备份**（导出可能不完整，这种残缺备份比没有更危险）
- 客户端**高于**服务端 → 只提醒，恢复时会有可忽略的参数告警

当前腾讯云 PostgreSQL 是 **16**，服务器上装匹配版本：

```bash
brew install postgresql@16          # macOS
apt install postgresql-client-16    # Debian/Ubuntu
```

找不到命令时可以用 `XINYI_PG_BIN` 指定目录。

### 2. 改了后端代码必须重启进程

Node 不热重载。2026-08-17 就踩过：改完图片压缩去前端测，上传成功但完全没压缩，因为跑的还是旧进程。**部署后务必确认进程重启过。**

### 3. 云厂商自带备份不能替代这套

腾讯云的自动备份继续开着，但它：① 只能整库回滚，恢复不了单张表；② 和数据在同一个账号下，账号出问题就一起没了；③ **不备份磁盘上的附件**。

这套是自己手里能验证、能带走的那份。

## 五、相关环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `XINYI_DB_URL` | — | 数据库连接串（必需） |
| `XINYI_BACKUP_DIR` | `.runtime/backups` | 备份输出目录 |
| `XINYI_UPLOAD_DIR` | `.runtime/uploads` | 附件目录 |
| `XINYI_PG_BIN` | 自动探测 | pg_dump/pg_restore 所在目录 |
| `XINYI_RESTORE_VERBOSE` | 关 | 打开后打印 pg_restore 完整告警 |

## 六、原理：为什么要存「指纹」

备份时记录每张表的**行数**和**内容校验和**（整行文本按序拼接取 md5），恢复后逐表比对。

只比行数是不够的——行数对得上、字段内容坏掉的备份照样是废的，而这种坏法只有在真出事那天去恢复时才会发现，那时已经晚了。

校验和能发现：字符集转换错误、JSONB 序列化差异、数值精度丢失、时区偏移。这几样都是「行数完全正常但数据已经错了」的典型。
