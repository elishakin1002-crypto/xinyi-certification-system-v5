## 第 2 条：我的“连接配置不同”没有证据，但 Claude 对配置来源的论证也不成立
我的回应：☑部分成立

理由和证据：

我撤回“服务连接的 PG 和 `.env.local` 不同”这个断言。登录失败本身证明不了连错库，应该先核对用户名；Claude 的对照实验支持“用错了那批用户名”的解释。

但 Claude 说“只加载两个文件，所以没有第二个连接来源”，这点错了：**进程启动时继承的环境变量也能提供 `DATABASE_URL`，dotenv 默认不会覆盖已有值。**

我核对代码：
```text
$ rg -n 'dotenv.config' server/app.js
8:dotenv.config({ path: path.resolve(__dirname, '../.env.local') });
9:dotenv.config();

$ rg -n 'connectionString:' server/authStore.js
351:    connectionString: process.env.DATABASE_URL,
```

再用项目实际安装的 dotenv 做无文件写入的实验：
```text
$ node -e 'const dotenv = require("dotenv"); const env = { DATABASE_URL: "inherited-example" }; dotenv.populate(env, { DATABASE_URL: "file-example" }); console.log(JSON.stringify(env));'
{"DATABASE_URL":"inherited-example"}
```

这证明“存在其他配置来源的可能”，**不证明那个进程确实用了不同配置**。我之前把可能性说成事实，是我的错；Claude 把可能性完全排除，也不对。两个库账号数同为 27，同样不能单独证明是同一个库。
