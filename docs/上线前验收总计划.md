## 本轮要执行的三块

按「出事了多严重」排序：

### A. 六条业务主线端到端（最高）

系统是不是"能用"，不取决于每个按钮点得动，取决于**一条真实的活能不能从头走到尾**。
每一步之后做「三看」：看下游（该出现的地方出现了吗）、看刷新（F5 还在吗）、
看换人（换个角色看得到吗、数字一样吗）。

| 角色 | 主线 |
|---|---|
| 销售 | 线索 → 转客户 → 建合同 → 录回款计划 |
| 总助 | 合同立项 → 指定负责人和交期 → 看谁手上重 |
| 顾问 | 接任务 → 改状态（进行中 / 跳过各一次）→ 记工作日志 |
| 财务 | 确认到账 → 看逾期 → 顾问结算 → 导出 |
| 总经理 | 六视角工作台 → 营收 → 战略 |
| 系统管理员 | 建号 → 分角色 → 停用 → 审计日志 |

### B. 危险按钮（次高）

删除、归档、停用、提交、确认、导入导出。
**做之前先备份**（CLAUDE.md 第三条），只在 `UAT-` 数据上测。
重点验三件事：
1. 该删不掉的确实删不掉（经手过记录的账号），而且提示说清为什么、该用什么代替
2. 删掉之后刷新、换角色再看一次 —— 这个项目出过「删了刷新又回来」
3. 连点三下会不会建出三条

### C. 边界输入（第三）

空值、超长、特殊字符（引号/尖括号/emoji）、重复提交、并发。
重点是**不报错但存错**那一类，不是"能不能弹错误提示"。

## 🔴 执行过程中查出的最大一条：安全网两周没跑过

这一条不在原计划的十个维度里 —— 它是跑「改完要验原本正常的东西还正常」
时撞出来的，而且它比前面所有条都严重。

| | |
|---|---|
| GitHub 远端最后一次提交 | **2026-09-04** |
| 本地领先远端 | **109 个提交**（两周的工作） |
| CI 最后一次运行 | 2026-09-04，**结果是 failure** |
| 生产上跑的版本 | `d9906cc`（9-15 部署）—— **这个提交 GitHub 上没有** |

三个后果：

1. **CI 配得很齐但形同虚设。** 类型检查、全量测试、构建、前端密钥扫描、
   迁移文件检查、权限矩阵体检、部署预检、E2E —— 八道闸门，
   **两周没有对任何一行新代码跑过**。我这轮新加的数据契约闸门也一样。
2. **代码只存在于这一台笔记本上。** 服务器上有部署出来的那一份（不含
   git 历史），但两周的提交记录、分支、每一次改动的理由，只有本机有。
   笔记本出事 = 这些全没了。这比数据备份那条更要命 ——
   数据还能从生产库恢复，代码历史不能。
3. **生产跑的代码在 GitHub 上找不到。** 真要排查线上问题，
   没法从远端 checkout 出对应版本。

不做的话会怎样：上线后线上出问题，想回滚到"上周那个能用的版本"——
而那个版本只在一台笔记本的 git 里。

**这一条要金总拍板：推代码到 GitHub 是对外动作，我不自己做。**
推之前建议先在本机跑一遍 `npm test` + `npx tsc --noEmit`（都是绿的），
推上去之后 CI 会跑全套 —— 大概率会红几条（e2e 里还有 3 条老选择器），
那正是它该干的事。

## 我对这份计划的一句话判断

**这个系统在"功能正确性"和"字段口径"上已经是能上线的状态**，
这两块查得比一般的内部系统细得多（317 个数字双人独立对账、
37 条字段口径逐条收口、契约进 CI）。

**真正的风险不在功能，在运维**：备份没有定时。
那一条不做，上面所有的都白搭 —— 所以它被单列成"上线当天第一件事"。
