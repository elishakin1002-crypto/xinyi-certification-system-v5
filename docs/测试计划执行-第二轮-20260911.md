## 一、最重要的发现：工作台上的「在制项目」数字，此前 100% 是假的

生产库实测：

```
状态       类别        数量
Active   + FollowUp    8      ← 全是旧的「认证到期挖角跟进」
Completed + Delivery   12
Completed + FollowUp    4
```

**一个在做的真实交付项目都没有。** 12 个客户项目全部已完成。

而此前工作台显示「在制项目 8 个、人均在制 3.67」—— 那 8 个**全是幽灵跟进项目**
（就是那个每 10 秒自动建项目的 bug 生出来的那批）。

所以这次改动**不是让数字变难看，是把假数字撤掉了**。现在显示：

```
在制项目总数 0  |  有活在手的人 0  |  未完成任务 0
```

三个数字互相一致，而且是实话。

> ⚠️ 这件事对测试有直接影响：四位同事登录后，
> 「在制项目」相关的看板会是空的 —— **那是数据的真实状态，不是 bug**。
> 要让这块有内容，得先有真实的在做项目。

## 二、「归档旧项目」不是正确解法

我原来提议把那 10 个「认证到期挖角跟进」整体归档。查下来这个方案是错的：

**系统里根本没有「已归档」这个状态。** Status 只有
New / Pending / Converted / Risk / Lost / Active / Completed。
硬塞只能改成「已完成」—— **而它们没有完成，那是在账本上写假话。**

真正的 bug 在别处：

```js
const activeProjects = inputs.projects.filter(p => p.status === Status.Active);
// ↑ 完全没有排除已停用的 FollowUp 类别
```

FollowUp 9/8 就退出项目管理了（标成 legacy、新建不出来），
**但统计口径一直没跟着改**。这是坑 #23「改分类字段时最容易漏的是连带」的又一次：
类别改了、界面改了、**统计忘了改**，于是每个数字都偏一点，而没人看得出偏在哪。

**改代码比改数据对**：排除一个已停用的类别是说实话，而且对未来同类数据一并生效。

## 三、连带查出的三处口径不一致

改完在制项目口径，工作台立刻出现**「在制项目 0 个，未完成任务 70 条」**——
人完全看不懂那 70 条在哪。顺着查出两个更老的问题：

| 问题 | 后果 |
|---|---|
| `openTasks` 从**全部项目**里数，包括已结项的 | 项目结项了，里面没勾完的任务是历史不是欠账，却一直算在「未完成」里 |
| **没排除 `Skipped`** | 跳过是主动决定（客户自行处理、标准变更），算进未完成会让人对着一个永远清不掉的数字发愁，延误率的分母也跟着虚高 |

加上在制项目本身，一共**三处口径**（老板 / 总助 / 个人）现在统一到两个判据：

```ts
const isLiveProject = (p) => p.status === Active && p.projectCategory !== 'FollowUp';
const openTasksOf   = (ps) => ps.filter(isLiveProject).flatMap(p => p.tasks).filter(isOpenTask);
```

`isOpenTask` 复用 `src/modules/taskFlow.ts` 的那一份，不在这里另写 ——
**同一件事多处实现是这个项目最高频的 bug 形态**（老板和总助看到的数不一样）。

已加测试钉住：不许再出现自己写的 `status !== 'Completed'`。

## 四、走第三方：我差点又造一套重复模型

你说「第三方服务各类服务都有」，我准备在 `Project` 上加 `outsourced` + `vendorPartner`。

**动手前才发现系统里早就有：**

```ts
export type ProjectType = 'Self-Operated' | 'Outsourced' | 'Joint';
vendorName?: string;       // 合作方
purchasingCost?: number;   // 外包成本 —— 正是我说的结算口径
```

但**全代码库 6 处都硬编码成 `'Self-Operated'`，没有任何界面能选**，所以它形同虚设 ——
**正因为看不见，我才差点又造一套。**

同一件事两套模型，正是这个项目栽过最多次的地方（contractRef 多态、权限三份、
铃铛两份、级联两套）。每次的代价都是「改了一处、漏了另一处」，而且不报错。

**教训：先找有没有现成的，再考虑加字段。加字段是最后手段，不是第一反应。**

### 界面

建项目表单加了「谁来做」下拉 + 合作方字段：

| 选项 | 行为 |
|---|---|
| 自己做 | 正常推荐负责人 |
| 外包给第三方 | **不推荐内部人**，提示「把合作方填上，否则将来查『这活谁做的』会断在这里」，合作方**必填** |
| 和第三方合作 | **仍然推荐负责人** —— 一起做的活，信义这边还是要有人管 |

最后一条特意区分开：把 Joint 也当外包一并拦掉，会出现「一起做的项目没人管」，
比不推荐更糟。已加测试。

### 生产实测

| 场景 | 结果 |
|---|---|
| 选「自己做」 | 有建议 ✅ |
| 选「外包」 | 不推荐人 ✅ + 提示正确 ✅ + 合作方字段出现 ✅ |
| 选「合作」 | 仍推荐人 ✅ + 合作方字段仍在 ✅ |
