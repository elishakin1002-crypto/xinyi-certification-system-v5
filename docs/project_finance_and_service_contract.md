## 费用口径统一与项目-服务建模契约

### 1. 对象定位

- Project（项目）：客户在一个时间窗口内的一次合作容器，可承载多项服务与多批交付，不以“单服务”拆分为默认策略。
- ServiceItem（服务项）：项目内部的工作流/交付流（Workstream）。用于表达“一个项目里有 10 项服务”的结构化清单与追踪状态。
- Task（任务）：执行层原子动作，可选归属到某个服务项。
- Contract（合同）：商业文书与回款计划承载体；合同可以关联项目（通过 contractRef 绑定）。
- Receivable（回款/应收节点）：现金流明细，仅用于“回款进度与异常”，不定义项目价值，不参与项目完结门槛。

### 2. 金额口径（唯一主线）

#### 2.1 唯一价值主数据：项目合同金额

- 字段：Project.projectAmount（项目合同金额，总账认知点）
- 状态：Project.costStatus ∈ {待补全, 已确认}
- 派生规则：
  - projectAmount > 0 ⇒ costStatus = 已确认
  - projectAmount 为空或 ≤ 0 ⇒ costStatus = 待补全

#### 2.2 从属数据：回款记录（现金流）

- 承载：Contract.receivables（签约首付/阶段款/尾款等）
- 定位：执行结果与现金流追踪
- 不得作为项目完结条件
- 可用于派生指标：
  - 回款进度 = 已回款合计 / projectAmount
  - 异常：已回款合计 > projectAmount（提示风险，但不自动改动主金额）

### 3. 项目完成判定（最终口径）

- 项目 Active → Completed 必须满足：
  - costStatus === 已确认
  - projectAmount > 0
- 不关心是否已存在回款记录
- 强制提示规则：
  - 若存在回款记录（Contract.receivables 非空）但项目未补录 projectAmount，则禁止完结，并提示“已存在回款记录，请先补录项目合同金额”。

### 4. 多服务项目建模规则

- 默认策略：一个合同（或一次合作）对应一个项目，不因合同内含多服务而拆成多个项目。
- 拆分例外：只有当服务项需要独立验收/独立结项、执行团队完全不同或周期显著不同（例如跨 6 个月以上）时才拆为多个项目。
- ServiceItem 仅用于结构化表达与进度追踪，不影响项目完结门槛。

### 5. UI 认知原则（防“双轨总账”复现）

- 页面只允许存在一个“总金额认知点”：项目合同金额（Project.projectAmount）。
- 回款明细必须以“从属明细/进度”呈现：
  - 显示每笔回款节点
  - 显示回款进度条与异常提示
  - 不出现第二个“总金额”入口（不得用回款合计代替合同金额）

### 6. 兼容与迁移策略

- 不使用回款反推项目合同金额。
- 历史项目若缺失 costStatus，按 projectAmount 派生归一化：
  - projectAmount > 0 ⇒ 已确认；否则 待补全。
- 若项目关联合同且合同本身存在 amount，可提供“一键带入合同金额”（用户显式确认后写入 projectAmount）。

### 7. 验收清单（必须逐条通过）

- 有回款但未填合同金额 → 不能完成，提示明确
- 只填合同金额，无回款 → 可以完成
- 填合同金额 + 回款 → 回款进度正确；回款 > 合同金额提示异常
- 页面只存在一个“总金额认知点”
- 一个项目可承载多服务项，且服务项清单可追踪状态；任务可选归属服务项
