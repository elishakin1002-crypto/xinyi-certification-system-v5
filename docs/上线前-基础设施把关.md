## 一、必须在上线前决定的（两条）

### 🔴 P0-1　备份是手动的，而且已经 7 天没备了

**实测证据**（2026-09-17 读生产，只读命令）：

```
crontab -l            →  空
systemd list-timers   →  没有 xinyi 相关的
/opt/xinyi/backups/   →  最新 xinyi-20260910（9月10日）
                          上一个 manual-20260903（9月3日）
```

`scripts/backup.mjs` 写得很好 —— 数据库 + 上传附件 + 指纹三样一起备，
`deploy/restore-drill.sh` 还能把备份恢复到临时库逐表核对。
**问题不在脚本，在于没人定时跑它。**

这正是 CLAUDE.md 二点五第 2 条自己写下的那句：
**「有个脚本可以跑」等于没有。**

**不处理会怎样**：下周起 13 个人每天录合同。如果哪天库坏了、
误删了、或者服务器出问题，能回到的最近状态是**一周前**。
一周的合同、回款、项目进度要靠人回忆重录 —— 而且没人知道漏了什么。

**建议**：做成 systemd timer（每天凌晨一次 + 保留 14 天 + 跑完校验行数），
和服务一起起来，不靠人记得。另外**每月跑一次 restore-drill**，
没演练过的备份只能算「大概能恢复」。

**工作量**：半天以内。改的是部署脚本，不碰业务代码。

### 🟠 P0-2　旧浏览器副本会覆盖别人刚存的数据（整份数据集写回）

**怎么发现的**：查「13 个人同时用会不会互相盖」时挖出来的。

**实测复现**（本机库，四步，2026-09-17）：

```
① A 打开页面，手里拿到当时的 projects 数组（10 个）
② 这期间 B 新建了一个项目                     → HTTP 201 成功
③ A 做了个无关操作，前端把它手里那份整数组推上去 → HTTP 200
④ 镜像 app_state_latest 里，B 建的那个项目：❌ 没了
   关系表 projects 里：                      ✅ 还在
```

**真因**：前端每次状态变化，会把 `contracts_v8 / projects_v8 /
customers_v8 / leads_v8 / settlements_v8 …` 这些**整个数组**推给
`POST /api/state/sync`。服务端有三方合并（base / 我的 / 库里现在的），
但 `protectedKeys` **只有三个**：

```
audit_issues_v1、project_work_logs_v1、task_templates_v1
```

其余一律「后写的赢」。

**影响面有多大 —— 实测后是精确的，不是最坏情况**：

界面上**看不到**这个问题，因为项目、合同、客户、线索、知识、结算、
情报都已经灰度切到 PG 直读，不再从镜像水合。实测：被覆盖之后，
总助打开项目管理仍然看得见 B 建的那个项目（共 11 个）。

真正暴露的是**只有镜像这一个来源、又没有三方合并保护**的数据集：

| 数据集 | 是什么 | 谁会受影响 |
|---|---|---|
| `strategic_tasks_v1` | 战略管理的必赢战役 | 总经理录的战役可能被别人的旧副本抹掉 |
| `strategic_insight_v1` | 战略洞察 | 同上 |
| `ai_decision_logs_v1` | AI 决策留痕 | 追溯「这个建议当时是谁批的」可能缺条 |
| `user_profiles_v1` | 用户档案 | — |

**还有一个次生影响**：`npm run checkup:consistency` 是拿镜像和关系表对账的。
镜像被旧副本盖过之后，这个体检会报出**假的不一致**，
或者反过来掩盖真的不一致 —— 体检报错狼来了几次，就没人看了。

**建议**（三选一，我倾向第 1 个）：

1. **把这几个数据集也加进 `protectedKeys`**（走已有的三方合并）——
   改动最小、机制现成，但要补测试验证合并对战略数据成立
2. 给 `/api/state/sync` 加版本号/时间戳校验：客户端的基线比库里旧就拒绝，
   前端提示「有人刚改过，请刷新」—— 更彻底，但要改前端交互
3. 把剩下几个数据集也切到 PG 直读 —— 最彻底，但上线前动这个太大

**不建议现在做的**：什么都不做。战略战役是老板亲手录的东西，
丢了他不会怀疑是并发，只会觉得系统不可靠。

**工作量**：方案 1 约一天（含测试）。

## 二、需要你拍板的业务口径（三条，我不替你定）

这三条是字段排查 37 条里**剩下没动的**。它们不是文案问题，
改名字会掩盖真正的差异，得先定业务上要哪一个。

### B04　「回款率」有三个不同的分母

| 在哪 | 分子 | 分母 |
|---|---|---|
| 合同页卡片 | 未归档且在当前范围内的已收金额 | **合同金额合计** |
| 回款概览卡片 | 全部合同的已收金额 | **回款节点计划总额** |
| 工作台趋势 | 近七个月已收 | **同期新签合同金额** |

三个都叫「回款率」，数字必然不同。

**要你回答的**：你平时说「回款率」的时候，心里算的是哪一个？
定下来之后，另外两个要么改名（带上分母），要么去掉。

### B05　「本周」有三种窗口

| 在哪 | 实际口径 |
|---|---|
| 项目日志 / 工时 | **自然周**（本周一零点起） |
| 顾问工作台日志条数 | **回看七天**（今天往前数 7 天） |
| 我的任务「本周内」 | **未来七天**（今天往后数 7 天） |

过去和将来被混成了同一个「周」。

**要你回答的**：要统一成自然周（周一到周日），还是保留三种但改名
（本周 / 近七天 / 未来七天）？统一成自然周要一起改边界，不能只换字。

### C04　「本月已收」算的是**到期月**，不是**到账月**

八月到期、九月才收到的钱，现在记在**八月**。
财务的回款趋势图同理。

**要你回答的**：这个口径你能接受吗？
- 能接受 → 我把标题改成「本月到期应收中的已收」，趋势图标注「按应收到期月」
- 不能接受 → 需要**新增一个"实际到账日"字段**，并把历史数据补上（这是数据结构改动，不是文案）
