# AI 中枢化治理改造方案（两选一）

本文件用于把“AI 是否成为系统大脑中枢”的目标落到可实现、可回滚、可验收的工程方案上。两套方案都遵循同一底线：安全/可维护性优先于花活。

## 1. 背景与问题（现状摘要）

现状关键点：

- AI 入口是全局的：ChatWidget 在 Layout 中全局挂载，任何页面可触发。
- AI 具备直接写主数据能力：通过 `<execute_action>{...}</execute_action>` 协议可创建客户/合同/提醒。
- 项目域铁律在 docs 中明确，但 ChatWidget 的跨域写入存在口径张力。
- 治理能力不足：缺少权限点、审计一致性、幂等、限流与脱敏等关键措施。

## 2. 共同目标（两方案都要满足）

### 2.1 安全与治理基线

1) 权限点：任何“写操作”必须经过统一权限校验（基于当前用户角色/权限模型）  
2) 审计日志：写操作必须可追溯（谁触发、输入摘要、模型、输出摘要、执行结果）  
3) 幂等：同一 AI 动作重复提交不会造成重复写入（至少对提醒/合同/客户提供幂等键策略）  
4) 错误码语义化：前后端对 AI 失败（429/400/500）有一致处理与用户提示  
5) 日志脱敏：禁止打印密钥；对客户名称/手机号/证照号等敏感信息做脱敏策略  
6) 限流：AI 网关（后端）应具备最小可用的限流与滥用防护

### 2.2 业务一致性底线

- “需要被盯、被催、被推进的事必须先变成项目”这一口径，要么落地为强约束，要么在 docs 中明确例外范围与理由。

项目触发规则（不可破）：

- AI、提醒、扫描、判断，一律只能从「项目」触发
- 没有项目 → 系统不得产生任何执行类行为
- 线索、客户、合同本身不具备执行能力
- 线索模块唯一允许的系统行为：创建跟进项目（手动或规则定时）

未成交客户“认证到期提醒”的标准流程（只认项目）详见：

- docs/project_execution_domain.md（未成交客户场景章节）

## 3. 方案 A：AI 成为“项目执行域大脑中枢”（强中枢）

### 3.1 核心思想

把 AI 的“执行权”限定在 Project Execution Domain：

- AI 只能对项目（project）产生可执行动作；
- AI 可以辅助创建客户/合同的草稿，但最终落库必须通过“项目域流程”或“用户确认”完成；
- 所有系统级提醒、扫描、推进都围绕 project 与 project.tasks 展开。

### 3.2 关键改造点（契约优先）

#### A) 动作协议升级（Execute Action Contract v2）

- 现状：`<execute_action>{...}</execute_action>` 内容无版本、无幂等键、允许跨域写入。
- v2 约束建议：
  - 必填：`actionId`（幂等键）、`projectId`、`type`、`payload`、`reason`
  - 禁止：无 projectId 的提醒创建；禁止直接创建“孤立提醒”
  - 版本：`version: "2.0"`

示例（概念，不是代码）：

- `ADD_REMINDER`：`{ actionId, projectId, type:"ADD_REMINDER", payload:{ content, priority }, reason }`
- `SUGGEST_TASK`：`{ actionId, projectId, type:"SUGGEST_TASK", payload:{ title, deadline }, reason }`

#### B) 执行器收敛（单一入口）

- 将 ChatWidget 的“动作执行”收敛到 AppContext 的统一执行器（例如 `executeAIActionV2()`），由执行器完成：
  - 权限校验
  - 幂等去重
  - 写入业务数据
  - 写入审计日志

#### C) AI 写入统一审计

- 复用/扩展现有 `aiDecisionLogs` 模型，让 ChatWidget 的动作也以同样口径记日志：
  - inputDigest（脱敏摘要）
  - outputDigest（脱敏摘要）
  - executedActions（actionId + 结果）

#### D) 项目域铁律落地

- ChatWidget 默认不直接创建客户/合同/提醒，改为：
  - 合同/客户解析结果生成草稿
  - 若需要推进/提醒：先创建/选择 project（跟进或交付），再由 project 执行器生成提醒/任务

### 3.3 影响评估

优点：

- 与 docs 口径完全一致；系统“可执行域”单一、清晰、可治理。
- AI 真正成为“项目大脑”：围绕项目持续诊断、扫描、推进的闭环更强。

代价：

- 改动涉及多个模块（ChatWidget、AppContext、提醒体系、合同创建流程），工程量更大。
- 用户体验会从“对话即写入”变为“对话 -> 草稿 -> 选择项目/确认 -> 执行”，需要 UI 支持与引导。

## 4. 方案 B：AI 作为“强助手但不拥有默认执行权”（弱中枢）

### 4.1 核心思想

保留全局入口与能力，但把“写操作”变为显式确认：

- ChatWidget 仍可在任意页面被唤起；
- AI 仍输出建议与结构化结果；
- 所有写入动作默认进入“待确认队列”，用户点击确认后才落库；
- 自动执行仅保留在项目诊断的“High 风险提醒”或也可同样改为待确认（按你偏好）。

### 4.2 关键改造点

#### A) 动作协议仍可用，但执行改为“两阶段”

- Phase 1（AI 输出）：生成 action candidates（候选动作）
- Phase 2（用户确认）：用户在 UI 勾选/确认后执行写入

#### B) 权限与审计仍必须补齐

- 即使是“用户确认”，也要补齐权限点、审计日志与幂等键，否则仍不可上线生产。

### 4.3 影响评估

优点：

- 改动相对小；基本不改变既有业务数据结构。
- 风险明显下降：减少 AI 误写/乱写的概率。

代价：

- AI 不再是“自动执行的大脑”，更像“强建议系统 + 半自动助手”。
- 与“项目域铁律”的一致性取决于你是否允许“非项目提醒”的存在（如果不允许，则仍需引入 projectId 约束）。
  - 如果采用“项目触发规则不可破”的口径，则方案 B 也必须做到：任何提醒最终都绑定 project（包括由 AI 输出的提醒候选）。

## 5. 两方案对比（建议决策表）

| 对比项 | 方案 A（强中枢） | 方案 B（弱中枢） |
|---|---|---|
| 与项目域铁律一致性 | 强一致 | 取决于是否约束提醒必须绑定项目 |
| 误写风险 | 低（强约束） | 中（靠确认降低） |
| 工程改动量 | 大 | 中 |
| 体验“即时闭环” | 中（多一步确认/选项目） | 高（仍可快速产出，但落库需确认） |
| 面向生产治理 | 最稳 | 稳（但仍需补齐治理项） |

默认推荐（在未进一步指定目标前）：

- 若目标是“AI 成为系统大脑中枢”且你认可项目域铁律：选方案 A。
- 若目标是“快速可用 + 风险可控”：先落地方案 B，再逐步演进到 A。

## 6. 验收标准（建议）

无论选 A/B，建议把验收写成可测试的条款：

- AI 不可用：CRM/合同/项目/财务/审计/知识库核心 CRUD 仍可使用。
- 任意 AI 写操作：必须有权限校验、审计记录、幂等策略、错误码语义化提示。
- 脱敏：日志与前端错误弹窗不泄露密钥与敏感字段。
- 限流：当触发 429 时，用户能看到明确提示且前端具备退避重试策略。

## 7. 回滚策略（建议）

为保证“小步提交、可回滚”，建议把改造拆为可回滚的开关：

- Feature Flag：`AI_WRITE_ACTIONS_ENABLED` / `AI_AUTO_EXECUTE_ENABLED`
- 回滚动作：
  - 关闭写入开关：AI 只生成建议，不落库
  - 关闭自动执行：所有动作进入待确认队列
