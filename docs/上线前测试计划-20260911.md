## 〇、先承认一件事

**你说得对。** 之前我一直是**散点排查** —— 聊到哪查到哪。

这种做法确实抓到了不少真问题（每 10 秒自动建项目、平板头像消失、
字段在映射里静默丢失、裸 SC 正则误判），但它有个**致命缺陷**：

> **永远不知道什么时候算测完了。**

散点排查给不出「哪些还没看过」这张图。而上线前真正要回答的恰恰是这个问题，
**不是「我们找到了多少 bug」**。

## 一、正规软件公司上线是怎么做的

标准流程大致七步。但**照搬到 13 个人的公司会失败** ——
不是因为不对，是因为没人会执行一份 80 页的文档。所以每一步我都标了「信义怎么做」。

| # | 标准做法 | 信义怎么做 |
|---|---|---|
| 1 | **测试计划**：范围、环境、角色、准入准出标准 | 就是这份文档，控制在能一次读完的长度 |
| 2 | **测试用例设计**：每功能/页面/角色写步骤和预期结果 | **从代码自动生成覆盖矩阵**，见下 |
| 3 | **冒烟测试**：最短主链能不能跑通 | 部署脚本里已有自检（服务/首页/鉴权/资源），每次部署自动跑 |
| 4 | **功能测试 + 回归**：逐条执行，改完再跑一遍 | 505 条自动化测试承担回归；人工只测自动化测不了的 |
| 5 | **UAT 用户验收**：真实用户用真实业务跑 | 佳佳、春姿、邦煜、智薇四个人 |
| 6 | **Go/No-Go 评审**：按准出标准决定上不上 | 见第五节，标准是可量化的 |
| 7 | **上线后观察期**：盯错误率和反馈 | 已有 `client_errors` 自动上报 + 每日 18:30 错误摘要推送 |

### 和大公司最大的差别

大公司靠**人力**覆盖（专职测试团队逐条点）。信义没有这个人力，
所以必须靠**两件事**替代：

1. **自动化承担回归** —— 505 条测试每次改动都跑，人不用重复点
2. **覆盖矩阵承担"没漏"** —— 从代码算出来，加一个页面矩阵自动变大

人工测试只花在**自动化测不了的地方**：界面好不好懂、流程顺不顺、
帮助答不答得上来、真实业务跑得通不通。

## 二、覆盖矩阵（从代码算出来，不手写）

```bash
node scripts/test-coverage-matrix.mjs          # 看矩阵
node scripts/test-coverage-matrix.mjs --cases  # 生成每人的用例清单
```

**为什么从代码算，不手写**：手写的清单必然漏，而且**漏在哪儿你不知道** ——
这跟散点排查是同一个毛病，只是换了个更正式的外壳。

脚本把三份东西交叉：
- 路由表（`App.tsx`）→ 有哪些页面
- `ROLE_PERMISSIONS` → 谁能看哪些页面
- `ROLE_CAPABILITIES` → 谁能做哪些动作

**加一个页面、加一个角色、加一个动作，矩阵自动变大，新格子自动是「未覆盖」。清单不会过时。**

### 当前规模

```
页面 16 个 × 角色 6 个 = 96 个格子，其中「该能进」75 个
动作 36 个，其中 30 个在自动化测试里出现过
```

## 三、矩阵立刻抓到的漏洞

这 6 个动作码在 `tests/` 里**一次都没出现过** —— 肯定没测过：

| 动作 | 谁会用 | 为什么要紧 |
|---|---|---|
| `LEAD_CONVERT` | 总经理/系统管理员/总助/销售 | **线索转客户是销售主链的关键一步**，断了整条获客链就断了 |
| `TASK_CREATE` | 总经理/系统管理员/总助/顾问 | 顾问每天都要加任务 |
| `KNOWLEDGE_WRITE` | 总经理/系统管理员/总助/顾问 | 知识沉淀是这个系统的护城河 |
| `REMINDER_WRITE` | **全部六个角色** | 覆盖面最广，却没测过 |
| `PROJECT_PAUSE` | 总经理/系统管理员/总助 | 项目暂停 |
| `SETTLEMENT_VIEW` | 总经理/系统管理员/财务 | 涉及钱 |

> 「出现过」不代表测得对，但**没出现过一定没测**。这张表找的就是后者 ——
> 这正是散点排查永远给不出的东西。

**这 6 个是上线前必须补的自动化测试**（见第六节排期）。

### 另外：关于第三方合作

你说「公司有不少服务项目是和第三方合作的」。

我现在只把**「其他许可」这一个大类**标成走第三方（医疗器械、饲料添加剂）。

**这个要你确认**：第三方合作是只限于那几类许可，还是各类服务都可能？
两种情况的做法完全不同。
