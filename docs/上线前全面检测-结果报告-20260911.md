## 三、修掉的真缺陷

### 三个新建接口：空请求体返回 500 而不是 400

`POST /api/leads`、`/api/customers`、`/api/projects` 收到空 body 时抛未捕获异常。

500 和 400 是两件事：400 是「你传的不对」，**500 是服务端自己崩了** ——
意味着可能已经写了半截数据，而前端只能说「服务器没有接受这次保存」，说不出哪里不对。

已补必填校验，文案说清后果：

> 「客户名称不能为空 —— 合同、项目、提醒都会引用它，空名字会让这些地方全变成空白。」

### 我自己引入的一个回归，当场抓住了

第一版给 `POST /api/projects` 也加了「负责人必填」，**打挂 5 条测试**。

查下来接口契约本来就允许**先建项目、再指派负责人**
（`POST /api/projects` 不带 manager → `PATCH /api/projects/:id/owner`），那是合法流程。
前端表单要求填负责人是**前端的策略**，不能拿它去收紧接口契约。

已撤销。**教训：补校验前先看现有测试和调用方在怎么用这个接口。**

## 四、我的检测脚本骗了我四次 —— 这一节最值得看

同一天四次，**每一次都伪装成产品故障**：

| # | 现象 | 真相 |
|---|---|---|
| 1 | 巡检 **OK/✗ 交替**，6 页报头像被盖 | 我用「点击 `div.fixed.inset-0.z-40`」关菜单，而那是**侧边栏容器**，点它反而把侧边栏打开了 |
| 2 | 巡检 **13 页全红** | 侧边栏被上一轮留在打开状态。差点以为刚部署的东西把生产搞挂了 |
| 3 | 鉴权矩阵 **62 处「总经理有权限却被 403」** | 我把**项目 id 填进了 `/api/leads/:id`**，资源查不到，授权层故障安全地拒绝 |
| 4 | 桌面宽度下巡检 **13 页全红** | 手机端和桌面端是两套 DOM 同时存在，`querySelector('[role="menu"]')` 永远取到**手机端那份**，而它在桌面下隐藏 |

**四次的共同点：脚本的假设只在我当时那个情况下成立。**
换个宽度、换个角色、换条数据就失真。

### 固化的五条对策（已写进脚本和坑文档 10c）

1. **每个用例前复位 UI 状态** —— 单页应用切路由不会重置组件状态
2. **关浮层用「再点一次触发器」**，不点任何遮罩
3. **脚本要有自检行**：复位没生效就标「本行不可信」，而不是当故障报
4. **查询要挑「当前可见的那一个」**，不能 `querySelector` 取第一个
5. **测试数据按资源类型给对**，拿不到就跳过并说明 ——
   **宁可少测一条，也不要报一条假的**

### 一条判断窍门

> **规律性的失败（交替、全红）通常是测试的问题；零散的失败才更可能是产品的问题。**
> 全红尤其可疑 —— 真实的产品故障很少这么整齐。

假缺陷比漏报更贵：它让人不再信这张表。
