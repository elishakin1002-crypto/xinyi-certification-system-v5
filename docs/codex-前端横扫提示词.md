# 给 Codex 的前端横扫提示词

> 用法：整段粘给 Codex。它会产出一份 `docs/前端横扫报告.md`，**只报不改**。
> 拿到报告后再决定修哪些、谁来修。

---

## 会话 X：前端一致性横扫（只查不改）

你在 `信义认证系统 V5.0` 仓库里工作。这是一家 13 人咨询公司的生产系统，
下周上线，13 个同事每天要用。

**这一轮你的任务是找问题，不是修问题。**
一行业务代码都不要改。只产出一份报告。

### 为什么是这样安排

我们之前的模式是「用户发现一个 → 修一个」，结果是拆东墙补西墙：
修了工作台的「逾期任务」，没修「我今天的活」，同一屏上两个数字互相矛盾；
修了后端的「标记已分拣」，没修前端的徽章，点了还是没反应。

所以这一轮要**横向拉平**：把同一类问题在所有页面上一次性找全，
再决定怎么改。找得全比找得准更重要 —— 拿不准的也列出来，标「待确认」。

### 刚发生的一个例子（这就是要找的那种问题）

用户用「合同识别」一次建了合同 + 客户 + 项目，然后：

```
合同管理 · 与我相关   有「浙江嘉力生物技术开发有限公司」
项目管理 · 与我相关   没有
```

真因：项目建出来了（两处存储里都在），但 `manager: '待指派'`、
`ownerUserId` 为空、9 条任务的 `owner` 也全是 `'待指派'`。
`isMineProject()` 的四条判据一条都不成立 ——
**不属于任何人，等于对每个人都隐藏**，包括刚刚亲手建它的人。

而拦截它的那行代码是 `if (!p.manager || p.manager === '待定') return null;`
—— 只挡了 `'待定'` 一个词，合同识别传的是 `'待指派'`。

注意这个 bug 的三个特征，你要找的都是这一类：
1. **不报错**。控制台没红字，测试全绿，页面能打开。
2. **同一个概念在两个页面用了不同的判据**。
3. **判空写成枚举几个已知的词**，别人换个说法就漏。

## 要扫的十类（按优先级）

每一类都给了「怎么扫」和「这个项目里已知的例子」。
已知例子是给你对齐标准用的，**不要只找这些，要找同类的其它处**。

### 第 1 类：同一个概念，多处实现，判据不一致 ★最高优先级

**怎么扫**：先列出这些「同名但可能各算各的」概念，
然后 grep 出每一处实现，把判据抄下来逐字对比。

必查的概念清单：

| 概念 | 界面上的说法 | 要对比的点 |
|---|---|---|
| 归属 | 「与我相关」「我的」「我负责的」 | 按 id 还是按姓名？算不算任务负责人？算不算服务项负责人？无主的怎么办？ |
| 逾期 | 「逾期任务」「已逾期」「超期」 | 当天到期算不算？没填截止日算不算？已结项项目里的算不算？已跳过的算不算？ |
| 进行中 | 「进行中项目」「执行中」「活跃」 | status 判据一样吗？归档的算不算？ |
| 未完成 | 「未完成任务」「待办」 | Skipped 算不算完成？ |
| 逾期回款 | 「逾期回款」「逾期未收」 | 没填到期日算不算？已收的排除了吗？ |
| 有效客户 | 「客户数」「活跃客户」 | 有合同才算，还是建了就算？ |

对每个概念产出一张表：

```
概念：归属（与我相关）
  pages/Projects.tsx:292   isMineProject      → ownerUserId | manager名 | 服务项owner | 任务owner
  pages/Contracts.tsx:???  ???                → ???
  pages/Customers.tsx:???  ???                → ???
  components/MyWorkWidget.tsx:??? ...
  结论：□一致  ☑不一致（具体差在哪：__________）
```

**已知**：归属在项目/合同/客户/线索四个页面各有一份，今天刚发现不一致。

### 第 2 类：判空 / 判类型写成「枚举已知的词」

**怎么扫**：grep 这些模式，每一处都问「别人写个别的词会怎样」。

```
=== '待定'|'待指派'|'未指派'|'待分配'|'暂无'|'无'|'未知'|'其他'
=== '' 或 length === 0 之后没有 .trim()
includes([...]) 判断类型 / 状态
switch 没有 default
```

**已知**：`buildProjectFromInput` 只挡 `'待定'` 漏了 `'待指派'`（已修）。
**要找的**：还有哪些地方在用同样的写法。

### 第 3 类：卡片数字 ≠ 下面的列表

**怎么扫**：每个页面的头部 4 张统计卡，逐张回答两个问题：

1. 这张卡的数字，和下面列表当前筛选出来的条数，**应该**相等吗？
2. 如果应该相等，代码里是**同一个数组算出来的**吗？

特别注意：卡片用的 `useMemo` 依赖数组里，**有没有把筛选器算进去**。
依赖里少一个筛选器 = 改筛选器卡片不动 = 同一屏两个口径。

**已知**：`pages/Projects.tsx` 注释里写过「四张都不跟随眼前的类别筛选
（useMemo 依赖里连 modeScope 都没有）」—— 确认这是有意的还是漏的，
如果是有意的，界面上有没有说清「这四张按全部算」。

要扫的页面（**所有角色的所有面板**，不是只看总助）：
工作台（六种角色各一套）、线索管理、客户管理、合同管理、项目管理、
不符合项管理、知识中心、财务、我的任务、情报雷达、战略管理、员工账号。

### 第 4 类：默认筛选把东西藏起来，且没告诉人

**怎么扫**：找所有 `useState` 初值不是「全部」的筛选器。
每一个都问：**筛出 0 条时，页面有没有告诉人「不是没有，是你在看某一档」？**

```
grep -n "useState<'all'" 、 useState('related')、useState('mine')、useState('active')
```

**已知**：`pages/Projects.tsx:98` `viewScope` 默认 `'related'`，
有提示（`你名下没有符合条件的项目，全公司还有 N 个` + 按钮）。
**要找的**：其它页面的默认筛选器有没有同样的提示。没有的列出来。

### 第 5 类：显示的是标志位，不是真实情况

**怎么扫**：找所有「已 XX」的徽章 / 状态标签，看它读的是什么。

- 读一个布尔字段 / 状态字符串 → **可疑**，标志位和事实可能不同步
- 真的去另一个数组里查了一遍 → 可信

**已知**：合同管理的「已立项」徽章用 `projects.find(p => p.contractRef === ...)`
真查项目 —— 这个是对的，拿它当标准。
**要找的**：「已转客户」「已开票」「已归档」「已分拣」「已结项」
这些徽章分别是怎么判的。

### 第 6 类：入口有，出口没有（闭环）

**怎么扫**：对每个「创建 / 转化 / 提交」动作，走完整条链：

```
点了这个按钮 → 生成了什么 → 那个东西在哪个页面能看到 →
看到之后下一步点什么 → 这条链断在哪
```

特别查：动作成功后的提示语有没有**告诉人下一步去哪**，
还是只说「操作成功」。

**已知**：立项之后有 `已立项「XX」—— {去哪看}，这样你才看得到它。`
这是标准。
**要找的**：其它动作的成功提示够不够这个标准。

### 第 7 类：字符串比较里的空值

**怎么扫**：
```
grep -n "|| ''" 附近有 < 或 > 比较
grep -n "String(.*) < \|String(.*) > "
```
`'' < '2026-09-15'` 是 `true` —— 所有没填日期的都会被算成「已过期」。

**已知**：工作台的「逾期未收 ¥173,400」就是这么来的（已修，见
`src/modules/glossary.ts` 的 `isReceivableOverdue`）。
**要找的**：还有哪些日期 / 版本号 / 编号在做字符串比较。

### 第 8 类：两处存储只写了一处

这个项目有两套存储：关系表（`server/repos/*.js`）和
`app_state_latest` 的 JSON 大对象。前端读后者，SQL 统计读前者。
只有 3 个数据集配了双向投影（见 `relationalProjection.js` 的 `PROJECTED`）。

**怎么扫**：找所有直接 `setXxx([...])` 改数组、但没有跟着
`commitTransaction` / 走 service 的地方。

**已知**：`addContract(createProject=true)` 是正确写法（一个事务写四个数据集）。
拿它当标准。

### 第 9 类：按「形状」猜，而不是显式声明

**判据**：这条规则**要不要随着别人写新代码而更新**？
要，它就早晚会错。

```
grep -n "\.fixed\.inset-0\|querySelector\|closest(\|match(/\\\\d+/\|split('-')\[\|startsWith('P-')\|id.length ==="
```

**已知**：这个项目已经错了五次（`.fixed.inset-0` 当弹窗错四次、
按 id 形状猜路径段错一次、`match(/\d+/)` 从 "ISO14001" 里抓出 "14001"
显示成「第 14001 期」）。

### 第 10 类：权限三份定义对不上

`ROLE_PERMISSIONS`（看哪些菜单）、`ROLE_CAPABILITIES`（做哪些动作）
都在 `constants.ts`，服务端还有一份解析出来的。

**怎么扫**：对每个角色，列出「菜单里能进的页面」和
「页面里的按钮点下去服务端会不会 403」。
典型症状是「菜单看得见，但每个请求都 403」。

另外注意：`checkActionPermission('X', {})` 和 `checkActionPermission('X')`
**结果相反** —— `{}` 是 truthy，会触发「这条数据是不是我的」判断，
而空对象谁都不属于。grep 所有传了 `{}` 的调用。

## 怎么验（重要）

**不要只读代码。** 这个项目的所有坑都有一个共同特征：
**不报错，但一直是错的** —— 测试是绿的、页面能打开、控制台没红字，
只是功能悄悄没生效。读代码读不出来。

所以每条发现都要给出**证据**，三选一：

1. **真跑一遍**：起本地服务（`npm run dev`，前端 3000 / 接口 3001），
   用不同角色登录，点到那个页面，截图或抄下界面上的数字。
2. **两处代码并排**：把不一致的两个判据原文贴出来，标上文件:行号。
3. **构造一条数据**：说清「如果某字段是 X，这里会怎样」，
   并且实际去库里查有没有这样的数据。

**没有证据的条目一律标「待确认」，不要写成结论。**
我宁可看到「疑似，没验」，也不要看到一个查不到根据的「已确认」。

## 输出格式

写到 `docs/前端横扫报告.md`，按这个结构：

```markdown
# 前端一致性横扫报告（YYYY-MM-DD）

## 一、必须上线前修（会让人看到互相矛盾的数字，或功能悄悄不生效）

### 1. <一句话说清症状，从用户角度>
- **在哪看到**：角色 / 页面 / 具体哪张卡或哪一行
- **两边分别是什么**：A 处显示 X（file:line），B 处显示 Y（file:line）
- **真因**：
- **证据**：□跑过 □并排代码 □查过库    具体是：
- **影响面**：还有哪几处是同一个原因
- **建议怎么改**：（只写思路，不要动手）

### 2. ...

## 二、上线后再说（不影响判断，但迟早出事）
（同样格式）

## 三、待确认（我拿不准，需要业务确认）
- 问题：
- 我的两种理解：A…… / B……
- 谁能回答：

## 四、扫过但没发现问题的（证明覆盖到了）
- 第 N 类 / 哪些文件 / 结论一句话
```

第四节不许省。**没写进第四节的，就当作没扫过。**

## 硬性约束

1. **一行业务代码不许改。** 这一轮只产出报告。
   （报告文件本身可以写。）
2. **不许跑破坏性命令。** 不删数据、不重置、不 `git checkout .`、
   不 `pkill -f "server/app.js"`（文件名会撞车，误杀过别人的开发服务器）。
   要停进程用 PID。
3. **3000 / 3001 可能被别的项目占用**，起服务前先
   `lsof -nP -iTCP:3000 -sTCP:LISTEN` 看清是谁的。
4. **测试跑不起来先看 Docker**：`docker start xinyi-dev-db`。
   这是本机环境问题，跟线上无关 —— 报告时要说清楚，
   别让人以为系统坏了。
5. **数量不封顶，但每条都要有证据。** 找到 40 条有证据的，
   比找到 100 条猜的有用得多。

开始前先读 `CLAUDE.md` 和 `docs/踩过的坑.md`，
后者按类别整理了这个项目已经踩过的坑，每条写清「症状 / 真因 / 怎么避免」。
你要找的就是同类的下一个。
