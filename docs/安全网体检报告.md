# 安全网体检报告

**2026-09-18 ｜ 提交基线 `e29c765` 之后**

## 这份报告回答一个问题

> 这个项目里所有的「安全网」，**现在还活着几张？**

不是问「跑起来是不是绿的」—— 绿只证明命令退出码是 0。
是问「**故意塞个坏东西进去，它红不红**」。

这个问法是这一天逼出来的。9 月 18 日一天里连着发现六个问题，串在同一根线上：

```
CI 的测试 glob 写错  →  测试一条没跑过
  → 修好后发现 Node 版本是 20（生产是 22）
    → 修好后发现 CI 根本没有数据库，63 条全 ECONNREFUSED
      → 加了数据库发现这套迁移建不出新库（018 依赖没人建的表）
        → 测试终于跑起来，才发现权限闸门从来没执行过（/glossary 裸奔）
          → 权限过了，才发现 e2e 在断言四个已经删掉的功能
```

**每一个都只有在前一个被修好之后才暴露** —— 因为后面的步骤一直被 skip。
六个问题形状完全一样：**看起来在工作，其实从没执行过。**

一个一个撞，永远不知道还剩几个。所以做了这次体检。

---

## 一、结论：9 道自动闸门，9 道有效

体检方式：往每道闸门里塞一个**真出过事**的坏东西，看它红不红。
基线先跑一遍确认是绿的（基线就红的话，变异测试什么都证明不了）。

| 闸门 | 塞进去的坏东西 | 结果 |
|---|---|---|
| 类型检查 | 把字符串赋给 number | ✅ 红了 |
| 单元测试（771 条） | 把「本月实收」改回按到期日算 —— 正是今天修掉的财务口径 bug | ✅ 红了 |
| 前端构建 | 引用一个不存在的模块 | ✅ 红了 |
| 前端密钥扫描 | 把 KIMI_API_KEY 写进前端代码 | ✅ 红了 |
| 迁移文件检查 | 加一个版本号重复的迁移 | ✅ 红了 |
| 权限矩阵体检 | 去掉一条路由的守卫 | ✅ 红了 |
| 字段契约 | 把合同表 title 字段改名 | ✅ 红了 |
| 部署预检 | 把接口鉴权令牌从环境里拿掉 | ✅ 红了 |
| 端到端（合同主线） | 把「录入合同」按钮文案改掉 | ✅ 红了 |

**工具留在仓库里**：`npm run audit:safety-nets`，
并且已经做成**每周一自动跑**（`.github/workflows/safety-net-audit.yml`）——
否则这次体检本身也只是「有个脚本可以跑」。

### 中途出过一次误报，值得记下来

第一轮 e2e 那条报的是「❌ 失效」。查下去发现是**我的变异点写错了**：
`replace('录入合同', ...)` 只换第一处，而第一处出现在**注释**里 —— 界面根本没变。
就算改对地方，e2e 用的是 `/录入合同/` **正则包含匹配**，加后缀也照样匹配得上。

**一个用来验别人的工具，自己犯了一模一样的毛病**（看起来在检查，其实没有）。
已改成和其它闸门一样的「锚点必须唯一命中」写法。

这件事说明变异测试不是万能的：**变异点本身也要验**。
所以每个变异点现在都强制唯一锚点，写错了会当场抛错，而不是静悄悄地报一个假结论。

## 二、真正的问题不在这 9 道，在另外 38 个

项目里有 **47 个「体检/检查」类脚本**。其中：

| | 数量 | 会自动跑吗 |
|---|---|---|
| CI 里的闸门 | 9 | ✅ 每次 push |
| **只能靠人记得跑的** | **38** | ❌ **从来不会自动跑** |

CLAUDE.md 自己写过这条判据：

> **「有个脚本可以跑」等于没有。** 状态快照攒到 146MB、`npm run checkup` 没人看，
> 都是因为它们是脚本而不是定时任务。

**这 38 个就是这句话的现状。** 没有任何记录能告诉我们它们最后一次执行是什么时候 ——
因为没有任何地方记录过。

### 抽查结果：12 个只读体检脚本，11 绿 1 红

我跑了其中 12 个不会写数据的：

```
checkup / checkup:coverage / checkup:ui / checkup:industry / checkup:data
checkup:knowledge / checkup:consistency / health:ui / health:dashboard
health:views / health:auth:gate            → 全部通过
health:data                                → ❌ 退出码 1
```

**`health:data` 现在是红的**，报的是：

> 1 条 `link_type='audit'` 的提醒指向已不存在的记录（AUD-1786946504171）
> → 用户点开会跳到空白，且这类记录会一直留在提醒中心

**这条只在本机开发库。生产库我去查过了，17 项检查全过、干净的。**
但重点不是这条脏数据本身，是：**一个会红的体检，红了多久没人知道。**

## 三、体检过程中顺带查清的两件事

### 1. 生产上没有任何一个定时任务

```
systemctl list-timers  →  全是系统自带的（logrotate / apt / sysstat …）
crontab -l             →  无
xinyi 相关 unit        →  只有 xinyi.service（后端进程本身）
```

也就是说，生产上**没有备份、没有巡检、没有对账**，一件自动的事都没有。
备份这条是已知的（放行标准 G1，按金总决定上线后做）；
**巡检和对账是这次才确认为零的。**

### 2. 生产业务数据目前是空的 —— 这让一部分体检「绿得没有意义」

```
线索      455 条        客户    0 条
账号       22 个        合同    0 条
用户档案   16 份        项目    0 条
                       提醒    0 条
```

所以生产那份「17 项全过」里，有相当一部分是**因为没东西可检查才过的**：
「回款合计未超过合同金额」——没有合同；「项目→客户引用完整」——没有项目。

**这是今天这个形状的第三种变体：**

> 绿色可能是「检查通过了」，也可能是「从没执行过」，
> **还可能是「执行了，但没东西可检查」。**

**直接影响放行标准 G6（财务核对关键数字）**：现在没有数字可核对。
G6 必须安排在 G4 之后 —— 真人走完六条主线，系统里才有第一批真实数据。

## 四、下一步建议（按优先级）

| | 事项 | 为什么 | 谁做 |
|---|---|---|---|
| 1 | **G4 六条主线真人走一遍** | 走完才有真实数据，G6 才做得了 | 各岗位同事 |
| 2 | **G6 财务核对**（G4 之后） | 现在系统里是空的，无从核起 | 财务 |
| 3 | **G5 应急一页纸填上手机号发全员** | 已写好，缺两个联系方式 | 金总 |
| 4 | **上线当天做掉定时备份** | 生产目前零定时任务 | 我（上线时主动提） |
| 5 | 把 38 个手动脚本收敛 | 要么做成定时任务，要么删掉 —— 留着等于自欺 | 我 |

第 5 条我的建议是**不要全做成定时任务**。
38 个里多数是一次性排查工具，做成定时只会多出 38 份没人看的日志。
应该挑出真正该定期做的那几条（数据对账、两处存储一致性、孤儿引用），
跟着服务一起起来；**其余的明确标成「一次性工具」，从体检清单里拿掉**——
清单里留着一堆没人跑的东西，本身就会让人不相信这份清单。

## 附：这次体检怎么复现

```bash
npm run audit:safety-nets           # 全部 9 道，约 10 分钟
npm run audit:safety-nets -- --fast # 跳过慢的（构建/e2e/全量测试），约 1 分钟
```

工作区不干净它会**拒绝跑**（它要改源文件再还原，不能和你的改动混在一起）。
跑完会再验一次工作区是否还原干净。
