## 现状与问题定位
- 当前 `TaskTemplate` 只有 `id/name/tasks`，不记录“创建者/更新时间/是否内置/是否归档”，因此无法做“谁能改/谁能删/怎么隐藏测试模板”。
- `AppContext` 只有 `addTaskTemplate`，没有 `update/delete`；UI（项目页模板按钮条）也没有管理入口。

## 两种方案（含影响评估）
### 方案 A：内置模板锁定 + 用户模板可自管（推荐）
- **规则**：
  - `TEMPLATE_*` 视为“内置模板（built-in）”：不可编辑/不可删除（避免破坏系统默认交付链路）；只允许“复制为我的模板”。
  - `TPL-*` 或普通模板视为“用户模板”：创建者可编辑/删除/归档；`ADMIN` 可管理所有用户模板。
- **优点**：安全、可回滚、责任清晰；不会因为误删内置模板导致“新建项目自动套模板”失效。
- **代价**：需要给模板加元数据并做一次本地存储迁移（可兼容旧数据）。

### 方案 B：所有模板都可改/可删（但需要更强审计/回滚）
- **规则**：允许 `MANAGER/ADMIN` 直接编辑/删除任何模板（含内置）。
- **优点**：操作最自由。
- **代价**：容易误删/误改导致系统模板链路断裂，需要引入“版本/回收站/审计记录”才能兜底；实现成本更高。

我将按**方案 A**落地：既满足“清理测试模板/修改自建模板”，又不破坏系统模板。

## 数据模型与接口改造（智能化基础）
1. **扩展 TaskTemplate 元数据**（兼容旧数据）：
- `createdByUserId/createdByName`
- `createdAt/updatedAt`
- `isBuiltIn`（内置锁定）
- `archived`（归档隐藏，代替硬删除的安全兜底）
- `usageCount/lastUsedAt`（智能排序：常用靠前）

2. **Context 增加模板 CRUD/归档能力**
- `updateTaskTemplate(templateId, updates)`
- `deleteTaskTemplate(templateId)`（仅对非 built-in，且满足权限）
- `archiveTaskTemplate(templateId, archived)`
- `cloneTaskTemplate(templateId, newName)`（内置模板“复制为我的模板”）

3. **权限设计（谁能删/改）**
- `ADMIN`：可编辑/删除/归档任何“用户模板”。
- 非 `ADMIN`：仅能编辑/删除/归档**自己创建**的模板。
- `built-in`：所有人不可编辑/删除（只允许复制）。

（如你希望“交付负责人也能删除全组模板”，后续可把 `MANAGER` 加到“可管理他人模板”规则中，但目前没有部门/团队边界字段，先做保守安全版。）

4. **智能排序与展示策略**
- 默认只展示 `archived=false` 的模板。
- UI 展示顺序：`lastUsedAt` 倒序，其次 `createdAt` 倒序。
- 归档模板在“模板管理”里可恢复。

## UI 交互改造（解决你说的痛点）
1. **项目详情模板条**
- 每个模板 pill 右侧提供“更多”入口（或长按）：
  - 自建模板：重命名/编辑任务列表/归档/删除
  - 内置模板：复制为我的模板

2. **新增「模板管理」弹窗**（移动端友好）
- 列表：模板名、来源（内置/我创建）、任务数、最近使用时间
- 支持搜索、查看归档、恢复归档

## 验证方式
- 新建模板 → 可重命名/编辑/删除/归档。
- 内置模板 → 不可编辑/删除，但可复制为我的模板。
- 切换不同用户/角色 → 权限符合预期。
- `npm run build` 通过。

## 回滚方案
- 仅影响 `taskTemplates_v1` 的结构：迁移为“向后兼容填默认值”，回滚代码后旧模板仍可正常读取（忽略新增字段）。
